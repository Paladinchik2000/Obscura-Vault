# Obscura Password Manager

Android, Kotlin + Jetpack Compose. Пакет `com.obscura`. Тема `ObscuraTheme`.
minSdk 24, targetSdk 36, compileSdk 37.

## Архитектура ключей — не менять без обсуждения

DEK (AES-256, случайный) — единственный ключ хранилища. На диск в открытом
виде не попадает никогда. Две обёртки:

- PIN: KEK = HMAC(keystore_pepper, PBKDF2(pin, salt, 210k)) → pin_wrapped_dek
- Биометрия: Keystore-ключ с setUserAuthenticationRequired → bio_wrapped_dek

Keystore-pepper (HMAC-SHA256, non-exportable) делает офлайн-перебор PIN
невозможным без физического устройства. Это и есть основная защита, а не
число итераций PBKDF2.

Ключ базы = HKDF-SHA256(DEK, info="obscura-db-key-v1") → SQLCipher raw
`x'<64 hex>'`. DEK напрямую в SQLCipher не передаётся.

### Ключ бэкапа НАМЕРЕННО устроен иначе

`BackupCryptoUtils` выводит ключ чистым PBKDF2(пароль, соль, 600k), без
Keystore и без DEK. Это выглядит непоследовательно на фоне `DatabaseKey`,
но менять нельзя: DEK привязан к Keystore конкретного устройства, а бэкап
восстанавливают на новом телефоне. Ключ бэкапа обязан быть переносимым.
Не «унифицировать» с HKDF от DEK ни при каких обстоятельствах.

## Правила работы с базой

- Инстанс `VaultDatabase` создаётся при разблокировке и закрывается при
  `lock()`. Глобального синглтона нет и быть не должно.
- Любое обращение к DAO — только через `VaultSession.runInSession`,
  `launchInSession` или `observe`. Не через `viewModelScope`.
- Многошаговые записи — через `VaultSession.runInTransaction`.
- `lock()`: stop accepting → `cancelAndJoin()` → `close()`, под `NonCancellable`.
- SQLCipher 4.19.0 не обнуляет переданный массив ключа и читает его заново
  при каждом новом соединении. Стирать только после `super.close()`.
- `System.loadLibrary("sqlcipher")` вызывается явно в `ObscuraApplication`.

## Формат файла бэкапа

`OBVB`(4) | formatVersion(2) | соль(16) | IV(12) | AES-256-GCM+тег.
Заголовок открытый и передаётся в GCM как AAD. Три разных исключения:
`UnsupportedBackupVersionException`, `BackupFormatException`, `SecurityException`.

Текущая версия формата — **2**. Читаются версии **1 и 2**
(`BackupCryptoUtils.SUPPORTED_FORMAT_VERSIONS`), пишется всегда текущая.
Версия 2 добавила массив `links` — связки записей с приложениями и сайтами
для автозаполнения; в файлах версии 1 их просто нет. Связка, указывающая на
запись, которой нет в файле, при импорте отбрасывается: внешний ключ не дал
бы её записать.

## Манифест

### Ориентация

Портретная ориентация фиксирована для всех Activity
(`android:screenOrientation="portrait"`): в ландшафте клавиатура PIN не
помещается на экран. Новые Activity обязаны объявлять portrait — это
проверяет инструментальный тест `everyActivityIsPortraitOnly`.

Ловушка на API 26: полупрозрачное окно с фиксированной ориентацией падает в
`Activity.onCreate` с `IllegalStateException: Only fullscreen opaque
activities can request orientation` (при targetSdk > 26; в 8.1 проверку
убрали). Проверено на эмуляторе API 26, включая контрольный прогон. Сейчас
полупрозрачных Activity в приложении нет — `AutofillUnlockActivity`
непрозрачная, — поэтому обходной путь через `values-v26`/`values-v27` удалён
вместе с легаси-экраном. Заводишь полупрозрачную Activity — помни про это.

Android 16 (targetSdk 36) на больших экранах игнорирует `screenOrientation`
(ChangeId `UNIVERSAL_RESIZABLE_BY_DEFAULT`; порог ≥ 600dp — по документации).
На планшетах фиксация не работает — поведение экрана входа в ландшафте там
не проверено.

### Разрешения в APK

Фактический список (`aapt2 dump permissions` release APK):

- `USE_BIOMETRIC`
- `USE_FINGERPRINT` (maxSdkVersion 28)
- `com.obscura.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` от androidx.core —
  signature-уровня, объявлено и запрошено (две записи).

`INTERNET` нет и не должно появиться: приложение офлайновое. После
изменения зависимостей проверяй список заново.

`PROVIDE_CREDENTIALS` ушло вместе с пустой заглушкой Credential Manager:
сервис не отвечал ни на один колбэк, а на Android 14+ Obscura при этом
предлагалась как провайдер. Passkeys — отдельная задача.

Видимость чужих пакетов даёт `<queries>` с intent `MAIN`/`LAUNCHER` — это
не разрешение, и в списке выше его нет. `QUERY_ALL_PACKAGES` не использовать.

`ObscuraAutofillService` защищён атрибутом
`android:permission="android.permission.BIND_AUTOFILL_SERVICE"` у `<service>`;
в `uses-permission` это не добавляется и в списке выше не появляется.

## Автоблокировка

Наблюдатель жизненного цикла живёт в `ObscuraApplication` на
`ProcessLifecycleOwner`, а не на `MainActivity`: хранилище может быть открыто
из автозаполнения, когда `MainActivity` вообще не запускалась. При уходе в
фон блокировка планируется (`VaultSession.onAppBackgrounded`), а не
проверяется при возврате, — иначе брошенное в фоне хранилище оставалось бы
открытым до следующего запуска. `ProcessLifecycleOwner` шлёт `ON_STOP` с
задержкой около 700 мс, поэтому «Immediately» на практике значит «почти
сразу», а не «в ту же миллисекунду».

## Внешние Activity и автоблокировка

Системный экран, который мы запускаем сами за результатом (SAF-пикеры
экспорта и импорта), — отдельная Activity: наша получает `ON_STOP`, и при
автоблокировке «Immediately» хранилище закрылось бы, а результат пришёл бы
уже на экран входа.

Поэтому любой такой запуск идёт только через `rememberVaultResultLauncher`:
он помечает `VaultSession` перед запуском и снимает пометку в колбэке
результата, включая отмену пикера. Льгота ограничена
`VaultSession.ownResultGraceMs` (2 минуты) — брошенный пикер не должен
держать хранилище открытым. Остальные уходы в фон блокируют как обычно.

Добавляешь новый запуск внешней Activity за результатом — используй этот
механизм, иначе «Immediately» ломает сценарий.

`BiometricPrompt` льготы не требует: в APK нет ни одной Activity от
androidx.biometric, а тест
`PickerAutoLockGraceTest.theBiometricPromptDoesNotStopTheActivity`
проверяет, что при вызове промпта `ON_STOP` не приходит. Отдельный случай —
`AutofillBiometricAuthActivity`: она разрешает `DEVICE_CREDENTIAL`, а
системный ввод PIN устройства это уже отдельная Activity. К сессии
хранилища тот экран отношения не имеет.

## Автозаполнение

`ObscuraAutofillService` заполняет формы (API 26+) и сохраняет логины,
введённые руками (API 28+).

### Сохранение логинов

Системный диалог «Сохранить в Obscura?» не показывает, что будет записано и
не заменит ли это пароль. Поэтому его «Да» только открывает наш экран
(`AutofillSaveActivity`), и в хранилище ничего не пишется без нажатия там.

- **Когда есть `SaveInfo`:** в каждом ответе для формы с полем пароля, на
  API 28+, никогда в самом Obscura (`SavePolicy`). В том числе в ответе для
  заблокированного хранилища. Ниже API 28 его нет: экран сохранения
  открывается через `SaveCallback.onSuccess(IntentSender)`, а он появился в
  28. Настройки на Android 8 прямо говорят, что сохранение недоступно.
- **Система сама не предлагает сохранить**, если значения не менялись после
  автозаполнения или совпадают с набором из ответа
  (`Session.showSaveLocked`, проверено по исходникам и тестом).
- **`onSaveRequest` ничего не пишет.** Он читает введённое и откуда оно:
  пакет из структуры от системы, сертификат из `PackageManager`, метку для
  названия. Всё это кладётся в `PendingSaves` — в память процесса, под
  случайным токеном. В `IntentSender` уходит только токен.
- **Экран сохранения не может подтвердить вызывающего:** система запускает
  его обычным `startIntentSender`, не за результатом, и `callingActivity`
  там null (измерено в `AutofillSaveTest`). Поэтому `ConfirmedCaller` тут не
  используется, а происхождение (`SaveOrigin`) создаётся только в
  `onSaveRequest` и попадает на экран только через `PendingSaves`.
- **Пароль** хранится как `char[]` и стирается, когда экран закрывается —
  как бы он ни закрылся, — при замене новым сохранением и через 2 минуты.
  Ни на диск, ни в intent, ни в `savedInstanceState` он не попадает. Строку,
  в которой его отдал фреймворк, обнулить нельзя: её только копируем и
  отпускаем. Смерть процесса — сохранение пропало, человек введёт снова.
- **Решение** (`SavePlanner`). Кандидаты — записи, сопоставленные
  приложению или сайту по правилам заполнения (нужен сертификат), плюс
  записи, из которых заполнялась форма (id набора = id записи). Логины
  сравниваются без пробелов по краям и через `lowercase(Locale.ROOT)`.
  Тот же логин и пароль — ничего не пишем. Тот же логин, другой пароль —
  «Update» по каждой записи или «Save as new», молча не перезаписываем. Иначе
  — новая запись.
- **Новая запись** — категория логинов (иначе её не предложат при следующем
  заполнении). Название: метка приложения из `PackageManager`, пакет — если
  метка не читается, для сайта — регистрируемый домен. Связка сразу: сайт
  для доверенного браузера, приложение с текущим сертификатом, и никакой,
  если сертификат не читается. Тогда экран предупреждает, а связку потом
  создаст пикер, где вызывающий подтверждается.
- **Хранилище заблокировано.** Сначала сводка с кнопкой «Unlock and save» —
  человек видит, ради чего разблокирует. После PIN всё, что не требует
  выбора, делается сразу: новая запись сохраняется, дубликат сообщается
  тостом. Второго вопроса нет. Узнать о дубликате до разблокировки нельзя:
  без DEK база не читается, а индекс паролей вне хранилища — это новая
  поверхность атаки, её не заводим.

### Сопоставление — это защита от фишинга, а не удобство

- Приложение опознаётся по имени пакета **и** SHA-256 сертификата подписи.
  Учитывается история подписей (ротация ключа по APK Signature Scheme v3),
  иначе после ротации все связки отвалились бы.
- `webDomain` из разметки — это утверждение приложения, а не факт. Ему верят
  только от браузеров из `TrustedBrowsers` (пакет + сертификат). Для всех
  остальных домен отбрасывается, и вызывающий матчится как приложение.
- Домены сравниваются по границам меток: `evil-bank.com` и
  `bank.com.evil.com` не совпадают с `bank.com`, `login.bank.com` совпадает.
  Сохранённое значение, равное публичному суффиксу (`co.uk`, `github.io`),
  не совпадает ни с чем — для этого в APK лежит Public Suffix List
  (`res/raw/public_suffix_list.gz`, обновляется руками, интернета у
  приложения нет и не будет).
- Предлагаются только записи категории логинов. Поле `urlOrCardNumber`
  считается сайтом, лишь если разбирается как хост.
- Ничего не совпало — ни одной записи, только пункт «Search Obscura».
- Сертификат читается через `getPackageInfo`, а с Android 11 чужой пакет нам
  не виден без `<queries>` в манифесте. То, что система привязала наш сервис
  автозаполнения, видимости не даёт: в коде автозаполнения AOSP 16 нет
  `grantImplicitAccess`. `<queries>` с `MAIN`/`LAUNCHER` покрывает приложения
  с иконкой. Пакет, который всё равно не виден, получает ответ с одним пунктом
  «Search Obscura» — без записей по связке или домену, сертификата ведь нет.
  Тихий `null` здесь запрещён: он неотличим от «нет подходящих записей», и
  именно так на телефоне молча не работало автозаполнение целиком.
- Когда приложение запускает наш пикер за результатом, система выдаёт нам
  видимость этого приложения (`ActivityStarter`, `grantImplicitAccess`).
  Эта видимость живёт только в памяти `system_server` (`mImplicitlyQueryable`
  в `AppsFilterImpl`, на диск не пишется): смерть процесса она переживает, но
  теряется при перезагрузке **и** при обновлении любого из двух приложений.
  Поэтому для невидимого пакета в выпадающем списке всегда только «Search
  Obscura», а связка срабатывает в пикере.

### Подтверждение вызывающего на наших экранах

`AutofillUnlockActivity` — и шаг разблокировки, и пикер — получает
вызывающего только через `ConfirmedCaller.confirm`, и подтверждение двойное:

- имя пакета из нашего intent совпадает с `getCallingActivity()`. Это
  измерено для обоих способов запуска экрана: и как аутентификация всего
  ответа (шаг разблокировки), и как аутентификация набора («Search
  Obscura») `callingActivity` — настоящее приложение, а не null
  (`theUnlockStepKnowsWhichAppStartedIt…`, `thePickerKnowsWhichAppStartedIt`);
- сертификат этого пакета читается.

Сопоставление записей и сохранение связок на этих экранах принимают тип
`ConfirmedCaller`, а не голый `CallerIdentity`: новая дорога на экран не
сможет обойти проверку незаметно. Прямой вызов `CallerIdentity.of` в
Activity — ошибка ревью. Сервис (`onFillRequest`) берёт пакет из
`AssistStructure`, которую даёт система, и подтверждения через
`callingActivity` не требует.

Подтверждённому вызывающему связанные записи показываются первыми и
выбираются без вопроса «Remember this choice?». Неподтверждённому — простой
список: связки не применяются, новая не сохраняется, шаг разблокировки не
отдаёт записи, а показывает список.

Связка уникальна по `(type, value, entryId)` — схема 3, миграция 2→3
схлопывает старые дубликаты, оставляя самую новую строку. Повторное
«Remember» заменяет связку, а не добавляет строку.
- Внутри самого Obscura заполнение не предлагается никогда.
- В подсказке только название и логин. Пароль не попадает ни в подсказку,
  ни в логи.

Хэши браузеров взяты из Android Password Store (коммит `282e9519ae5c`) и
переведены в hex; Chrome сверен с реальным APK на эмуляторе.

Samsung Internet в списке APS нет, его хэши добавлены отдельно, и их два:
браузер подписан разными ключами. На Galaxy-устройствах это «CN=Samsung Cert,
O=Samsung Corporation», на остальных телефонах — «CN=Samsung Platform Key for
non-Galaxy devices». Оба взяты с APKMirror (раздел APK certificate
fingerprints, проверено 22.09.2026), то есть с зеркала, а не с устройства.
Снимешь `apksigner verify --print-certs` с телефона — сверь и допиши источник.
Ошибка в таком хэше может только отнять доверие, но не выдать его: неузнанный
сертификат означает, что домен из разметки отбрасывается.

### Разблокировка из автозаполнения

Заблокированное хранилище отвечает `setAuthentication`, а не данными:
до разблокировки из приложения не уходит ни один секрет. Разблокировка — PIN
Obscura или отпечаток через `BiometricPrompt`; `DEVICE_CREDENTIAL` запрещён,
иначе PIN телефона открывал бы все пароли.

`PendingIntent` — `FLAG_IMMUTABLE`; в него кладутся только `AutofillId`
полей и имя вызывающего пакета, никаких секретов. Датасеты собираются уже
после разблокировки, в нашем процессе. Проверено сквозным тестом: связка
immutable + аутентификация автозаполнения работает.

### Тесты

- JVM: `DomainMatchingTest`, `AutofillMatcherTest` — сценарии фишинга.
- Эмулятор: `AutofillEndToEndTest` гоняет настоящий системный UI через
  uiautomator, форма для него лежит в `androidTest` и потому выглядит как
  чужое приложение. Форма написана на Java: она работает в процессе тестового
  APK, где Kotlin-рантайма приложения нет.
- На этом эмуляторе (API 36) фокус на поле сам по себе сессию автозаполнения
  не начинает — тестовая форма вызывает `AutofillManager.requestAutofill`.
  Это особенность окружения, а не приложения.
- **Инструментация и её цель всегда видят друг друга** (`AppsFilterImpl`:
  «if either package instruments the other, mark both as visible»). Поэтому
  сквозные тесты с формой в `com.obscura.test` package visibility не
  проверяют: `AutofillEndToEndTest` был зелёным, пока на телефоне Obscura не
  видела ни одного приложения. Любой тест автозаполнения, который должен это
  покрывать, обязан использовать форму в пакете без инструментации.
- Такая форма — модуль `:autofilltarget`, отдельное приложение в двух копиях:
  `com.obscura.autofilltarget` с иконкой в лаунчере и `.hidden` без неё. APK
  упаковываются в assets androidTest и ставятся самим тестом через stdin
  `pm install` — только на то устройство, где идёт тест. Форму тест запускает
  через shell (`am start`), а не из нашего процесса: запуск чужой Activity
  может выдать пакетам видимость друг друга.
  `AutofillPackageVisibilityTest` проверяет обе копии. Контрольные прогоны:
  без `<queries>` падает тест копии с иконкой, с тихим `null` вместо «Search
  Obscura» — тест скрытой копии. Там же связки в пикере: применяется без
  вопроса, с чужим сертификатом не применяется, повторное связывание не
  плодит строк, после `pm install -r` целевого приложения видимость пропадает
  (контроли: «всегда спрашивать» и «связка по одному имени пакета» роняют
  свои тесты).
- `AutofillSaveTest` — сохранение через настоящий системный UI с
  `:autofilltarget` (там кнопка «Sign in» вызывает `AutofillManager.commit()`):
  новая запись со связкой, дубликат при заблокированном хранилище, смена
  пароля, сохранение сразу после разблокировки, «Not now» стирает пароль,
  невидимое приложение без связки. Контроли: без `SaveInfo`; дубликат и
  смена как новая запись, повторное подтверждение после разблокировки;
  пароль не стирается и связка без сертификата.

## Правила для тебя

- Перед изменением криптографии сверяй примитивы с внешним эталоном
  (OpenSSL), а не только со своими тестами.
- Утверждения про поведение библиотек проверяй по байткоду или исходникам,
  не по памяти и не по аналогии с прошлой версией.
- Криптография и жизненный цикл ключей проверяются инструментальными
  тестами на эмуляторе. JVM-тесты на фейковой базе проверяют твою модель
  Room, а не Room.
- Инструментальные тесты гоняй ТОЛЬКО на эмуляторе. К компьютеру бывает
  подключён телефон с реальными данными, а `connectedDebugAndroidTest`
  идёт на все подключённые устройства и удаляет приложение после прогона.
  Перед каждым прогоном проверяй `adb devices` и задавай целевой
  эмулятор явно: `ANDROID_SERIAL=emulator-XXXX ./gradlew
  connectedDebugAndroidTest`. Если в списке нет ни одного эмулятора —
  подними его, а не запускай прогон «как есть».
- Коммить после каждой завершённой задачи.
- Не расширяй видимость `internal` ради тестов.
- Путь проекта не должен содержать запятых: `-Xfriend-paths` разбивается
  по запятой, и тесты перестают видеть `internal`.

## Слияние бэкапов

При «Объединить» побеждает большее `updatedAt`, при равенстве — запись из
хранилища. `updatedAt` берётся с часов устройства: при сильном расхождении
часов между устройствами «более свежей» окажется запись с того, где часы
убежали вперёд. Это принятое ограничение — бэкап здесь восстановление, а не
синхронизация. Не вводить векторные часы без реальной задачи синка.
